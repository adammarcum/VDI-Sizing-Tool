What it does

From user counts to a recommendation

VDI Host Sizer replaces the manual spreadsheet behind a VDI host sizing. You describe the desktops, it keeps every assumption visible, so the number you give the customer is one you can defend.

1
Describe

Enter the workloads

One row per desktop user type and per RDSH farm, with names you choose: concurrent users, vCPU, memory, vGPU, disk and profile storage.

2
Size

Calculate the host count

Hosts needed for CPU, memory, vGPU memory and an optional VMs-per-host cap. The largest wins, then N+X failure tolerance and the minimum cluster size are added.

3
Validate

Check it with hosts failed

The design is re-tested at N-X: vCPU:pCore (and with hyper-threading), GHz per user, memory and GPU left, and VMs per host.

4
Deliver

Hand over a branded report

One click produces an AHEAD-branded report with the workloads, host sizing, storage, assumptions and method. It works offline, can be emailed and prints cleanly to PDF.

Also built in

Compare up to three hosts

Put candidate hosts side by side, with a processor picker for current Intel Xeon and AMD EPYC models that fills in cores and base clock.

Host count override

Enter a fixed node count (for example a quoted configuration) and see at once whether it passes the design rules.

Storage that adds up

Thick/PVS, Instant Clone / MCS and profile storage for desktops and RDSH combined, with dedupe and a free-space reserve.

vGPU aware

vGPU profile memory per desktop is sized against GPU memory per host. A host with no GPU is flagged instead of quietly passing.

Workload classes

Each user type gets a vCPU:pCore design limit by class, so light task desktops and heavy power users are not sized on the same ratio.

Growth and clusters

Compound annual growth for a future sizing, and automatic splitting into several clusters when the total exceeds your cluster cap.

Licensing

Per-core licensing with the 16-core-per-CPU minimum, for the recommended host count.

Saved projects

Save a sizing and reopen it later with all of its settings from your local project library.

Update notice

How it works

Four steps to a sizing

Once the tool is running, a typical sizing takes a few minutes.

Enter the workloads

On Workloads, add a row for each desktop user type and RDSH farm. Name them anything you like and set the workload class.

Choose the host

On Hardware, pick a processor, memory and GPU memory for up to three candidate hosts.

Tune the rules

On Recommendation, set N+X, overhead, vCPU:pCore limits, dedupe and growth, and watch the host count and design check update live.

Download and save

Add the customer name and logo on Report, click Download report, and Save project to come back to it later.

Tip: Home → Load example opens a worked sizing (250 persistent desktops on an 8-host cluster) so you can see every screen before entering your own data.

Under the hood

How the number is calculated

Every step is shown in the tool and the report under "Sizing method", so the recommendation can be explained line by line. The method follows the AHEAD VDI Sizing Estimator.

Demand

What the workloads need

  • Desktops: cores = vCPU × users, memory = RAM × users, vGPU memory = profile × users.
  • RDSH: servers = users ÷ users per server, rounded up; then the same per server.
  • Disk per desktop: (thick disk + RAM) + (image × clone % + RAM) + profile. RAM is added for the swap file.
  • Storage: desktop and RDSH disk combined, divided by the dedupe ratio, plus an optional free-space reserve.
Hosts

How many, and does it hold up

  • Usable host: cores and memory minus the CPU and RAM overhead you reserve (10% by default).
  • Hosts needed: the largest of CPU (cores to keep each class within its vCPU:pCore limit), memory, vGPU memory and an optional VMs-per-host cap.
  • Final: plus X failure-tolerance hosts (N+X), never below the minimum cluster size, split into clusters above the cap.
  • Checks at N-X: vCPU:pCore, with hyper-threading (×1.3), GHz per user, memory and GPU remaining, VMs per host.
Planning defaults

vCPU:pCore design limits by workload class

These are industry rules of thumb used as starting points, not vendor-mandated limits. They are editable in the tool and will be reviewed by AHEAD; confirm them against the customer's standards or a pilot before committing to a design.

Questions

FAQ and troubleshooting

The most common first-run questions. The ReadMe in the download has more.

What do I need to enter?
For each desktop user type: the concurrent desktops, vCPU, memory, vGPU profile (if any), disk and profile size. For RDSH: concurrent users and users per server, plus the server vCPU and memory. Then the candidate host: processor, memory and GPU memory.
Why does the tool recommend fewer (or more) hosts than my spreadsheet?
The spreadsheet takes the host count as an input and shows how loaded it would be. VDI Host Sizer calculates the count from CPU, memory and vGPU limits, so the two can differ when someone typed in a more conservative number. Use Host count override to test a fixed count, and the reserve settings (CPU and RAM overhead, N+X) to build in extra headroom. The built-in example reproduces the spreadsheet's results exactly.
Are the vCPU:pCore limits official?
No. They are planning defaults based on common industry ranges and are pending AHEAD review. Change them under Recommendation → Design rules to match the customer's standards or pilot results.
Is storage performance included?
No. The tool sizes storage capacity only. IOPS, network, vSAN design and application licensing should be confirmed during design.
Which hypervisors and brokers does it cover?
Version {{VERSION}} targets VMware ESXi hosts for Horizon-style VDI and RDSH. Other platforms are not covered.
"The libraries could not be downloaded"
The first run needs internet access to pypi.org and files.pythonhosted.org. Connect (and join VPN if required) and run the launcher again. If a proxy blocks those sites, ask your eTech team to allow them.
Windows: "Could not open requirements file" or "files were not found"
The launcher was opened from inside the ZIP. Right-click the ZIP, choose Extract All... (for example to Documents), then double-click Run_on_windows.bat in the extracted folder.
Mac says "Apple could not verify … is free of malware" / "Not Opened"
macOS blocks scripts downloaded from the internet as a ZIP. Use the one-command install, which avoids the prompt entirely. The command downloads and builds everything on your Mac, so nothing is flagged. Already got the prompt? Click Done, then run the one-command install; it fixes the folder and the app. The first time you open the VDI Host Sizer app, macOS may ask to let it control Terminal: click OK.
How do I update to a new version?
The sidebar (under About) shows an Update available card when a newer version is on GitHub. On a Mac, run the one-command install again. On Windows, click Download update and replace the old files. Your saved projects are kept because they live in ~/HostSizer/VDIProjects, not in the tool folder. The launcher installs any new libraries automatically.
Can I turn off the update check?
Yes. Set the environment variable VDI_HOSTSIZER_NO_UPDATE_CHECK=1 before starting the tool. The check only reads the version number from GitHub.
